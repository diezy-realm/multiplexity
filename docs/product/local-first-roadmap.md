# Multiplexity — audit produk dan roadmap local-first

Tanggal kajian: 25 November 2026. Baseline: working tree lokal 0.3.0, yang berisi perubahan di luar commit Git terakhir. Sumber eksternal dan detail per produk: [riset integrasi enterprise](enterprise-integration-research.md).

Verifikasi lokal: `cargo test --locked --manifest-path rust/Cargo.toml --quiet` lulus 24 tes. Pengujian ini memakai fixture. Konektivitas dan izin instance enterprise, pengalaman pilot, dan kompatibilitas installer/data pengguna belum diuji dalam audit ini.

## Keputusan produk

Posisikan Multiplexity sebagai **workbench investigasi developer on-prem**. Alur utamanya: buka bukti → kaitkan service, environment, repo, dan revisi → analisis dengan sumber → tinjau diff lokal → validasi. Pengguna pertama adalah developer yang sudah memiliki akses perusahaan ke satu service dan bergantian membuka log, build, report, dan editor. Pilot: satu tim, satu service non-produksi, satu checkout lokal, dan satu provider AI yang disetujui.

Mulai dari alur **Log OpenShift → Evidence Case → Ask AI → Diff lokal**. Tambahkan impor report untuk menguji nilai produk tanpa mengandalkan API vendor. Pilihan konektor pertama: Bamboo jika pencarian build log paling banyak memakan waktu, atau SonarQube jika triase finding lebih sering. Riset eksternal juga menawarkan jalur Jira → Bitbucket → Bamboo untuk tim yang berangkat dari tiket. Pilih jalur itu jika pilot menunjukkan developer biasanya memulai dari tiket dan perlu menelusuri PR/build untuk mendapatkan bukti. Validasi dengan 5–10 kasus nyata yang sudah disanitasi dan wawancara singkat dengan pengguna pilot. Pakai jumlah perpindahan tab, median waktu menuju diagnosis yang memiliki bukti, porsi diagnosis dengan source+revision, dan jumlah patch yang dapat ditinjau sebagai metrik. Catat baseline sebelum pilot. Hipotesis awal: waktu diagnosis turun 25% tanpa transfer bukti yang tidak diizinkan atau edit di luar workspace. Angka ini target pilot, bukan hasil.

## Bentuk produk

- **Investigate** menjadi entry point untuk kasus aktif. Awali dengan service mapping manual: nama, environment, namespace/workload, repo, dan revisi jika diketahui. Evidence Item menyimpan asal, waktu, identitas target, status redaksi, dan referensi. Simpan snapshot terbatas secara lokal saat dipilih. Log tanpa revisi ditandai sebelum AI menyarankan lokasi kode.
- **Workspace** menyatukan checkout yang dipilih pengguna, diff, Artifact, dan Snippet. Pertama, buat patch yang bisa ditinjau. Saat apply, periksa repo/HEAD dan kondisi file, tolak patch basi atau di luar root, dan beri cara undo. Gunakan worktree terisolasi jika memungkinkan. Pisahkan apply lokal, menjalankan tes yang dipilih pengguna, commit, push, dan pembuatan PR.
- **Infrastructure** mengelompokkan VM/SSH, OpenShift, Kong, dan Databases. **Integrations** di Settings menampilkan koneksi, versi/edisi, health, identitas, scope, dan kemampuan. Tampilkan build, finding, dan ticket di konteks service di Investigate sebelum memberi masing-masing menu permanen.
- **Activity** menyimpan audit lokal untuk permintaan perubahan, persetujuan, dan hasil. Untuk aksi remote pertama, operator manual memilih satu target non-produksi, melihat aksi yang tepat, mengonfirmasi, lalu melihat status setelahnya. Hasil timeout/unknown harus bisa dibedakan dari sukses. Perubahan config menyusul setelah alur review dan verifikasi mapan.
- Mulai dengan **adaptor bawaan di Rust**. Pisahkan kemampuan baca dan tulis per koneksi, simpan secret dalam penyimpanan OS, gunakan TLS/trust store perusahaan, catat data yang keluar per provider, dan jangan mengirim bukti otomatis sewaktu preview. Evaluasi MCP kemudian untuk integrasi baca yang dipilih organisasi. MCP/CLI pihak ketiga membutuhkan pembatasan file/network dan izin per tool sebelum dipakai dalam workflow enterprise.
- **Local-first berarti data kerja tersedia lokal.** Kasus, Artifact, dan antrean draft yang sudah disimpan tetap bisa dibuka tanpa VPN. Log terbaru, API perusahaan, dan model cloud memerlukan jaringan. Bedakan status offline, data cache dan bukti segar. Mode browser terhubung ke backend loopback yang dijalankan pengguna, dan pemilihan checkout hanya tersedia saat backend lokal dapat memverifikasi root yang dipilih. [Arsitektur loopback](../rust-migration.md#local-web-development)
- **Gerbang pilot konektivitas.** Uji CA internal, VPN/proxy, dan policy provider. Implementasi konektor existing mempunyai jalur untuk menerima sertifikat invalid. Gunakan profil pilot dengan verifikasi TLS aktif dan CA perusahaan yang sesuai. [Implementasi TLS integrasi](../../rust/app/src/integrations.rs#L102)

## Keputusan setelah pilot

Bitbucket atau GitHub Enterprise berikutnya jika mapping checkout/commit manual menjadi hambatan. Jira ditambah jika handoff kasus sering terjadi. Checkmarx dan SCA punya nilai awal lewat impor report, lalu tambah API ketika versi dan hak akses instance terkonfirmasi. Confluent masuk setelah ada use case yang jelas seperti triase consumer lag atau perubahan skema, dengan scope metadata dan tanpa membaca event payload secara default. Tunda membuat menu per vendor hingga frekuensi dan kebutuhan navigasi terukur.

Sebelum memilih konektor pertama, konfirmasi edisi dan versi yang berjalan, cara akses dari laptop, metode autentikasi yang disetujui, scope minimum, retensi log/report, dan satu sample run yang boleh dipakai. Jira dan Bitbucket Data Center perlu diverifikasi per produk. SCM GitHub Enterprise Server perlu diketahui apakah Actions aktif. Istilah SAC belum didefinisikan dalam kebutuhan ini. Jika yang dimaksud SCA, fokus pada temuan dependency dan bukti versi dari lockfile/SBOM. Jika SAC adalah sistem internal yang berbeda, identifikasi pemilik, kontrak, dan satu contoh report terlebih dahulu.
